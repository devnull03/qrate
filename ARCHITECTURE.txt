# Qrate Architecture Documentation
# High-Performance CSV Editor with RevoGrid + SQLite Backend

## Overview

Qrate is a specialized CSV editing application that treats workspace files (.qrate)
as relational databases rather than flat text files. This architecture achieves
three critical goals:

1. O(1) Load Times: Opening a 1GB file is nearly instantaneous because data is paged
2. Crash-Resistant Reliability: ACID transactions prevent data corruption
3. Rich Workspace State: Configuration (column widths, sorting, views) stored alongside data

## Technology Stack

### Frontend
- **Svelte 5** (Runes mode) - Reactive UI framework
- **SvelteKit** - Application framework with SSR disabled for grid pages
- **RevoGrid** (@revolist/svelte-datagrid) - High-performance virtualized data grid
- **Tauri v2 API** - Frontend-backend communication via IPC

### Backend
- **Rust** (Tauri v2) - Native application runtime
- **rusqlite** - SQLite database driver with bundled SQLite
- **dashmap** - Concurrent hash map for connection management
- **csv** - CSV parsing for import operations

### File Format
- **SQLite 3** (.qrate extension) - Database file format
- **WAL Mode** - Write-Ahead Log for better concurrency
- **Custom Schema** - Three-table structure for data, columns, and metadata

## Architecture Pattern: "Headless Document Model"

Unlike traditional web apps that load data into RAM, Qrate treats the frontend
strictly as a VIEWPORT. The actual data resides on disk (in SQLite) and is
managed by Rust.

### Data Flow

1. User scrolls grid viewport
2. RevoGrid detects need for rows 100-150
3. Svelte calls `tauri::invoke('get_rows', { limit: 50, offset: 100 })`
4. Rust queries SQLite and returns only those 50 rows as JSON
5. RevoGrid renders the chunk

This prevents loading entire datasets into memory.

## Database Schema

### Table: _meta (Workspace State)
Stores configuration that CSVs cannot support:
- key: TEXT PRIMARY KEY (e.g., "viewport_scroll_y", "zoom_level")
- value: TEXT (JSON value or primitive)

### Table: _columns (Column Definitions)
Metadata for each column:
- id: TEXT PRIMARY KEY (e.g., "col_0", "col_1")
- name: TEXT (Display name/header)
- type: TEXT (Data type: Text, Number, Date)
- width: INTEGER (Column width in pixels)
- hidden: INTEGER (Boolean flag for visibility)

### Table: data (The Content)
Dynamic columns approach with TEXT affinity:
- row_id: INTEGER PRIMARY KEY AUTOINCREMENT
- [col_0]: TEXT (dynamically added columns)
- [col_1]: TEXT
- ... (additional columns as needed)

## Backend Architecture (Rust)

### Connection Management (app_state.rs)

```rust
struct AppState {
    connections: DashMap<String, Arc<Mutex<Connection>>>
}
```

- DashMap provides thread-safe concurrent access
- Each open file has a dedicated connection
- File path is used as the connection key
- Supports multiple files open simultaneously

### Database Operations (database.rs)

Core functions:
- init_database() - Create new .qrate file with schema
- open_database() - Open existing .qrate file
- get_rows() - Paginated data fetching for virtual scrolling
- update_cell() - Single cell updates with instant persistence
- add_column() - Dynamic column addition via ALTER TABLE
- update_column() - Column metadata updates (width, hidden state)
- insert_row() - Add new rows
- delete_row() - Remove rows
- import_csv_data() - Bulk import from CSV files

### Tauri Commands (lib.rs)

IPC interface exposed to frontend:
- create_qrate_file(path) -> FileOpenResponse
- open_qrate_file(path) -> FileOpenResponse
- close_qrate_file(path)
- get_rows(path, limit, offset) -> DataResponse
- update_cell(path, row_id, column_id, value)
- add_column(path, column)
- update_column(path, column)
- insert_row(path, values) -> row_id
- delete_row(path, row_id)
- import_csv_to_qrate(qrate_path, csv_path) -> FileOpenResponse

## Frontend Architecture (Svelte 5)

### Store Layer (qrateStore.svelte.ts)

Reactive store using Svelte 5 runes:

```typescript
class QrateStore {
    currentFilePath = $state<string | null>(null)
    columns = $state<ColumnDef[]>([])
    totalRows = $state<number>(0)
    rows = $state<Record<string, any>[]>([])
    isLoading = $state<boolean>(false)
    isFileOpen = $state<boolean>(false)
    error = $state<string | null>(null)
}
```

Provides high-level API that wraps Tauri commands and manages local state.

### Component Architecture

│   ├── Import CSV

### RevoGrid Integration

RevoGrid is used via the official Svelte 5 adapter (@revolist/svelte-datagrid):

```svelte
<RevoGridComponent
    source={revoRows}
    columns={revoColumns}
    theme="compact"
    resize={true}
    range={true}
    readonly={false}
    on:afteredit={handleCellEdit}
    on:aftercolumnresize={handleColumnResize}
    on:afterviewportscroll={handleScrolling}
/>
```

Key events:
- afteredit: Cell value changes, triggers update_cell() command
- aftercolumnresize: Column width changes, triggers update_column() command
- afterviewportscroll: Viewport scrolling, triggers get_rows() for new data

## Performance Optimizations

### 1. Virtual Scrolling
- Only render ~100 rows at a time
- Load new chunks as user scrolls
- Previous chunks can be garbage collected

### 2. Batch Operations
- CSV imports use transactions for bulk inserts
- Reduces I/O overhead significantly

### 3. SQLite Optimizations
- WAL mode enables concurrent reads during writes
- PRAGMA synchronous = NORMAL balances safety and speed
- Cache size increased to 64MB for better performance
- Temp store in memory reduces disk I/O

### 4. Debouncing
- Scroll events debounced to prevent excessive SQL queries
- Column resize updates debounced to reduce writes

### 5. Lazy Column Operations
- Column deletion is "soft" (hidden flag) to avoid table rewrites
- Hard compaction (VACUUM) only on explicit user action

## Save Strategy

### Auto-Save Model
Because we use SQLite, every cell edit is instantly saved to disk via UPDATE:
```sql
UPDATE data SET [col_0] = 'value' WHERE row_id = 5
```

No traditional "Save" button needed - changes persist immediately.

### Save As / Export
To create a copy:
```sql
VACUUM INTO 'new_file.qrate'
```
This flushes the WAL file and creates an optimized copy.

## Future Enhancements

### Possible Features Enabled by .qrate Format

1. **Undo/Redo**
   - Implement undo_log table tracking previous cell values
   - Works even after closing and reopening the app

2. **Cell Comments**
   - Separate table: comments(row_id, col_id, text)
   - Rendered as indicators in grid

3. **Data Validation**
   - Store regex rules in _columns table
   - Validate on edit with visual feedback

4. **View Presets**
   - Save specific filters/sorts in _meta table
   - Quick switching between saved views

5. **Formulas**
   - Store formula expressions in cells
   - Recalculate on dependency changes

6. **Cell Formatting**
   - Store styles in separate table
   - Apply conditional formatting rules

## Security Considerations

1. **File System Access**: Limited to user-selected files via dialog
2. **SQL Injection**: Protected via parameterized queries (rusqlite)
3. **Memory Safety**: Rust prevents buffer overflows and memory leaks
4. **Data Integrity**: ACID transactions ensure consistency

## Performance Benchmarks (Expected)

- Load time for 1GB file: < 1 second
- Scroll latency: < 50ms
- Cell edit persistence: < 10ms
- CSV import (1M rows): ~5-10 seconds
